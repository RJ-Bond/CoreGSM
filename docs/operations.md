# Эксплуатация: порядок действий

Что делать, когда панель нужно обновить, восстановить, проверить или она ведёт себя не так. Команды `coregsm` выполняются на сервере с панелью
(от root, кроме `status`, `doctor`, `logs`).

## Команды

| Команда | Что делает |
|---|---|
| `coregsm` | меню управления |
| `coregsm status` | состояние сервисов |
| `coregsm doctor` | диагностика и отчёт, который можно приложить к обращению |
| `coregsm logs [backend\|bot\|nginx-proxy]` | журналы сервиса |
| `coregsm update [--check] [--force] [--yes]` | обновить (с `--check` только проверить, есть ли новая версия) |
| `coregsm rollback [--yes]` | откатить последнее обновление вместе с базой |
| `coregsm backup` / `coregsm restore [файл]` | создать копию / восстановить из копии |
| `coregsm start\|stop\|restart` | управление контейнерами |
| `coregsm reset-password` | сбросить пароль администратора |
| `coregsm domain` | сменить домен или IP |

## Обновление и откат

- **Обновление** берёт релиз (или ветку `main`, если задано `UPDATE_CHANNEL=main` или `UPDATE_BASE_URL`; канал по умолчанию выбирается в
  «Настройки → Обновления и копии»). Перед миграцией базы рядом кладётся согласованная копия (`backups/pre-migrate-v<N>-<время>.db`, хранятся пять последних).
- **Не запустилось после обновления.** Сообщение о миграции в `coregsm logs backend` называет номер и причину. Выполните `coregsm rollback`: вернётся прежняя
  версия и база. Если нужно вручную: остановить (`coregsm stop`), заменить `coregsm.db` нужной копией `pre-migrate-…db`, запустить прежнюю версию.
- **Проверка до обновления.** Панель сама показывает «есть новая версия» и список изменений на вкладке «Обновления и копии».

## Резервные копии

- Расписание и число копий задаются в «Настройки → Обновления и копии» (раз в день или раз в неделю, хранится заданное число). Копии можно шифровать
  паролем, отправлять на другой сервер и в S3.
- **Проверка восстановления.** Раз в неделю панель сама открывает свежую копию так, как это делает восстановление (расшифровка, распаковка, проверка базы), и показывает
  результат на странице копий и в «Внимании» админки. Копия, которую никто не открывал, остаётся надеждой, а не копией.
- **Восстановление.** `coregsm restore` или «Восстановить» на странице копий (загрузка файла). Перед восстановлением панель делает копию текущего состояния.
- **Журнал изменений настроек.** Если сломали настройку, а не данные, копия не нужна: «Настройки → Обновления и копии → История настроек» возвращает прежнее
  значение одной кнопкой.

## Наблюдение

- **Метрики Prometheus.** Задайте `METRICS_TOKEN` (не короче 16 знаков) в `.env`: появится `GET /api/metrics` с `Authorization: Bearer <токен>`. Готовая панель
  Grafana и правила оповещений лежат в [docs/monitoring](monitoring/README.md).
- **Здоровье.** В админке «Система»: версия, диск, память, база, сертификат, диагностика. «Внимание» собирает то, что требует действия (сервер не отвечает,
  бот не подключён, нет копий, мало места).
- **Скорость у посетителей.** Там же карточка «Скорость у посетителей» (LCP, INP, CLS, TTFB по страницам). Её можно отключить.

## Частые случаи

| Симптом | Что смотреть |
|---|---|
| Сервер «не отвечает», хотя игра работает | порт запроса (query port) и брандмауэр; `coregsm logs backend`; кнопка «Опросить» на странице сервера; точки проверки покажут, виден ли он снаружи |
| Бот не пишет в канал | «Админка → Discord»: мастер подключения (токен, приглашение, права на канал); `coregsm logs bot`; служебные сообщения идут в канал оповещений |
| Нет писем | «Настройки → Безопасность → Почта»: проверка соединения; без почты письма не уходят, остальное работает |
| Забыли пароль администратора | `coregsm reset-password` |
| Мало места | «Система → Хранение данных» (сколько занимает история; сроки задаются `HISTORY_DAYS` и соседями); старые копии удаляются по числу хранимых |
| Сертификат HTTPS | «Система → Сертификат» показывает срок; продление выполняет установщик (`coregsm doctor`) |
| Панель за своим прокси | поток живых обновлений `/api/live` не должен буферизоваться: в nginx `proxy_buffering off` и длинный `proxy_read_timeout` (в поставляемом nginx уже настроено) |

## Переменные окружения (`.env`)

Самые полезные; полный список читайте по `process.env` в коде.

| Переменная | Смысл |
|---|---|
| `DOMAIN`, `PUBLIC_URL` | адрес панели и публичный адрес для ссылок и превью |
| `TZ` | часовой пояс процессов |
| `JWT_SECRET`, `SECRETS_KEY` | подпись сессий и шифрование секретов в базе; менять осторожно (секреты придётся ввести заново) |
| `INTERNAL_TOKEN` | пароль между backend и ботом |
| `SETUP_TOKEN` | код первого запуска |
| `POLL_INTERVAL_SEC`, `POLL_CONCURRENCY` | как часто и сколькими параллельными запросами опрашивать (по умолчанию 30 с и 8) |
| `HISTORY_DAYS`, `PLAYER_SESSIONS_DAYS`, `ACCOUNT_EVENTS_DAYS`, `UPTIME_DAYS` | сколько дней хранить каждый вид записей (по умолчанию 30, 90, 180, 90) |
| `METRICS_TOKEN` | включает `/api/metrics` |
| `UPDATE_CHANNEL`, `UPDATE_BASE_URL` | канал обновлений (`main` или релиз) и свой источник |
| `PROBE_TOKEN`, `PROBE_INTERVAL_SEC` | точки проверки на другой машине |
| `LOG_LEVEL` | подробность журнала |

## Образы контейнеров

При выпуске версии (workflow `release`, только по команде владельца) те же исходники собираются в четыре образа и кладутся в реестр GitHub:
`ghcr.io/<владелец>/coregsm-backend`, `coregsm-bot`, `coregsm-frontend`, `coregsm-nginx`. Теги: номер версии и `build-<id сборки>`; каждый образ подписан
без ключей (cosign, личность этого workflow), дайджест виден в журнале шага. Установщик пока их **не использует**: сервер по-прежнему собирает образы сам из
`install.sh`. Образы нужны, чтобы следующий установщик мог скачать готовое и не тянуть 12 МБ исходников; сбой этого шага выпуск не ломает.
Проверка подписи: `cosign verify ghcr.io/<владелец>/coregsm-backend:<версия> --certificate-identity-regexp 'https://github.com/<владелец>/CoreGSM/.github/workflows/release.yml@.*' --certificate-oidc-issuer https://token.actions.githubusercontent.com`.

## Общие типы API

Формы ответов, которые знают и бэкенд, и панель, лежат в `src/shared/types` и копируются в оба пакета командой `node tools/sync-shared.mjs`
(см. `src/shared/README.md`). Копия, которая отличается от оригинала, ломает тест бэкенда. Сейчас так описаны баны; остальные типы переезжают по мере правок.

### Готовые образы вместо сборки на сервере (по желанию)

Если на сервере установлен `cosign`, в `.env` можно добавить `COREGSM_PULL_IMAGES=1`: при обновлении установщик скачает четыре образа **этой же сборки**
(тег `build-<id>`), проверит подпись каждого (по дайджесту, личность workflow `release`) и запустит их без сборки на несколько минут. Нет `cosign`, нет образа этой
сборки в реестре (сборка не из релиза) или подпись не прошла: ничего не берётся, идёт обычная сборка. Владелец образов по умолчанию `rj-bond`, другое имя в `COREGSM_IMAGE_OWNER`.
Откат по-прежнему работает: образы получают те же локальные имена, что и собранные.
